# Comprehensive Code Review Workflow

このワークフローは、コード変更を多角的にレビューするための手順です。

## 使い方
ユーザーに以下の情報を確認してください：
1. レビュー対象（PR番号、ディレクトリパス、またはファイルリスト）
2. レビューの種類（小規模修正 / 新機能追加 / リファクタリング / 包括的レビュー）

その後、適切なステップを実行します。

---

## Parallel Review Phase: 3つの視点での同時レビュー
**実行タイミング**: 包括的レビュー、または複数の視点が必要な場合

> [!IMPORTANT]
> **このフェーズを実行する前に**、必ず後述の「レビュー種類別のフロー」を確認してください。  
> レビューの種類（小規模修正 / 新機能追加 / リファクタリング / 包括的レビュー）に応じて、実行すべきレビュワーが異なります。判断に迷うならユーザーにどれを実行するか聞いてください。

以下の3つのレビューを**並行して**実行してください。それぞれの専門エージェントが異なる視点から分析を行います。**忖度は一切せずにレビューさせてください。**

```
以下の3つのタスクを並行して実行してください：

1. @change-impact-reviewer: 変更されたファイルの影響範囲を分析（破壊的変更、リスクレベル）
2. @architecture-reviewer: 対象ディレクトリの構造と依存関係を分析（整合性、循環依存）
3. @code-reviewer: 変更されたファイルを1つずつ詳細にレビュー（実装品質、テスト、型安全性）
```

---

## Fact-Checking Phase: レビュー結果の検証
**実行タイミング**: Parallel Review Phase完了後、ユーザーに結果を返す前

3つの視点からのレビュー結果を統合する前に、以下のファクトチェックを**必ず**実施してください：

```
以下の項目を確認し、ハルシネーションを防止してください：

1. **コード引用の検証**
   - レビュー結果で言及されたファイルパス、クラス名、関数名が実在するか
   - 引用されたコードスニペットが実際のコードと一致するか
   - 行番号の参照が正確か

2. **指摘事項の根拠確認**
   - 指摘された問題が実際にコード上に存在するか
   - 改善提案が対象コードの文脈に適合しているか
   - 複数のレビュワーで矛盾する指摘がないか

3. **影響範囲の妥当性確認**
   - 言及された依存関係が実際に存在するか
   - 影響を受けると指摘されたファイルが実在し、関連性があるか
   - リスクレベルの評価が具体的な根拠に基づいているか

4. **レビュー結果の整合性確認**
   - 3つのレビュワーの指摘内容に矛盾がないか
   - 重複した指摘を統合できるか
   - 未検証の推測や仮定が含まれていないか
```

**検証方法**:
- 実際のコードファイルを再確認
- grep_search や view_file で事実確認
- 不確実な情報は削除または「要確認」として明記

---

## レビュー種類別のフロー

### 🔹 小規模な修正（1-2ファイル程度の軽微なもの）
- @code-reviewer のみ実行

### 🔹 新機能追加/ファイル数が多い場合など
- @architecture-reviewer と @code-reviewer を並行実行

### 🔹 リファクタリング
- 3つのレビュワーすべてを並行実行

### 🔹 包括的レビュー
1. Parallel Review Phase（3つのレビュワーを並行実行）
2. **Fact-Checking Phase（レビュー結果の検証）**
3. 統合サマリーの作成
