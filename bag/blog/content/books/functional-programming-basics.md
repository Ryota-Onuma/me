## 概要

関数型プログラミングの基礎から実践までを体系的に解説した一冊。純粋関数、イミュータブルな値、型による安全性といった概念を、具体例を交えながら丁寧に説明している。

---

## 第1章：命令型と宣言型

プログラムの書き方には2つの思想がある。

| 思想 | 特徴 |
|------|------|
| **命令型** | 「How（どうやって）」に注目。for、ifなどを駆使して逐次処理を書く |
| **宣言型** | 「What（何を）」に注目。「〜は〜である」という表現で追っていく |

:::important
**関数型プログラミングの考え方**
- 嘘をつかない関数を組み合わせて処理を組む（シグネチャを見れば何をするか自明）
- 関数は極力宣言型である
- 値のみを扱う（文ではなく式だけを使う）
:::

---

## 第2章：純粋関数

**純粋関数**とは:
- 戻り値は常に1つ（1種類）
- **引数にのみ**基づき、戻り値を計算する
- 既存の値を変えず、変更済みのコピーした値のみを返す

:::tip
**純粋関数の特性**
- 副作用がない
- 単一責任である
- 参照透過性がある（同じ値を与えたら必ず同じ値のみを返す）
:::

純粋関数はシグネチャを見ただけで挙動が推論しやすく、命令型のアプローチよりもバグを減らしやすい。また、入力に対して出力をユニットテストすることが容易である。

---

## 第3章：イミュータブルな値

:::message
**関数型プログラミングの定義**
イミュータブルな値を操作する純粋関数を使うプログラミング
:::

### 共有ミュータブル状態の問題

ミュータブルで複数の場所から参照されるものは、常にどこで更新されるかを追い続けないといけない。プログラムの複雑度が一気に上がり、プログラマは追いきれなくなる。

**解決策**: イミュータブルな値のみを操作し、返す純粋関数を使う。引数を直接更新せず、コピーして作ったインスタンスを更新し、それを返すことで副作用を防ぐ。

---

## 第4章：関数を値として扱う

- **高階関数**: 別の関数を受け取ったり返したりできる関数。関数は値なので、入力としても渡せるし、出力として返すこともできる。
- **カリー化**: 複数引数の関数を1引数ずつの関数に分解する変換。関数の再利用や合成が容易になり、宣言的プログラミングの基盤となる。

---

## 第5章：データ処理のパイプライン

### パイプライン処理

同じ型を返す小さい関数を連鎖的に呼び出し処理を進める。小さい処理から大きな処理を作る。

- リストを`map`、`filter`、`flatMap`などで連結して処理していくのは関数型プログラミングでよくあるパターン
- **for内包表記**: flatMapでのパイプラインが深くなったら、可読性を上げるために使える

### 文と式

- **文（statement）**: 実行するが値を返さない
- **式（expression）**: 評価すると値になる

関数型プログラミングでは式しか基本使わない。

### Option型

シグネチャに嘘をつかせないために存在する。値があるかないかを型で明示する。

---

## 第6章：関数型設計とエラーハンドリング

### 関数型設計

小さなブロックから大きな機能を構築する。純粋関数を小さな純粋関数から組み立てる。

:::warning
**例外をスローさせない**
純粋関数は常にシグネチャが正直であるべき。例外のようにシグネチャに現れないものを返す関数は純粋関数ではない。
:::

**代わりにOption型で明示的に返す**ことで:
- 呼び出し元が`None`の場合のハンドリングをせざるを得なくなる
- エラーもイミュータブルな値として扱える
- 宣言的に値のチェーンでエラーハンドリング（合成）できる

### エラーハンドリングのパターン

| パターン | 説明 |
|---------|------|
| **ベストエフォート型** | エラーが起きても処理を止めず、全部やり切る。成功と失敗を分けて扱う |
| **オールオアナッシング型** | 処理の中でエラーが起きたら全体を失敗とする |

### Either型

Optionのようにサブタイプを持つが、`None`の代わりに任意の型を返せる。通例、`Left`にエラーの内容、`Right`に成功時のデータを入れる。

## 第7章：型による安全性

### プリミティブ型の問題

プリミティブ型は意味を含ませられないため、本当だったら許容できない内容を渡しても、型が合っていれば通ってしまう。

### 解決策

| 手法 | 説明 |
|------|------|
| **ゼロコストラッパー（newtype）** | プリミティブ型のラッパー。コンパイル時は別物、実行時はプリミティブとして動作 |
| **直積型** | data classなど。複数のフィールドを持つ型 |
| **直和型** | enumとして実現。有限集合の値だけを取れる型 |
| **代数的データ型** | 直和型の要素が直積型。微妙に違うものを包括して管理できる |

```scala
enum YearsActive {
  case StillActive(since: Int)
  case ActiveBetween(start: Int, end: Int)
}
```

### パターンマッチング

直和型に対して使える。具体的な値をcaseで列挙し、網羅的に処理する。直和型に新たに値を追加したら、マッチングを追加しないとコンパイルエラーになる。

## 第8章：I/Oと副作用の分離

:::important
**関数のもつれを解く**
副作用がある関数を、純粋関数と非純粋関数に分け、関数型プログラミングの世界は純粋関数からのみ成り立つようにする
:::

### IO型による分離

1. I/Oを実行する処理のラッパー関数を定義
2. ラッパー関数はIO型の値を返すが、ラップしている関数の呼び出しはしない
3. ラッパー関数は純粋関数となり、呼び出し元は副作用を気にせず扱える
4. 副作用は関数型の世界の外で、`unsafeCall`を遅延実行することで起きる

**実行を後回しにすることで関数型の世界を純粋に保てる。**

### 関数型コア

ロジックを純粋関数に。副作用を外に。依存は引数として値で受け取る。

## 第9章：再帰とストリーム

### ボトムアップ方式

完成系のシグネチャから中身を書いていくトップダウン方式とは反対で、最低限必要な純粋関数から少しずつ積み上げていって、要件を満たす最終的な関数まで行き着く方法。

### 再帰関数

便利だがスタックオーバーフローのリスクあり。

| ケース | 対策 |
|--------|------|
| 有限の計算を期待する再帰 | ベースケース（出口となる処理）が必要 |
| 無限データ構造としての再帰 | 遅延評価が必要 |

遅延評価を導入することで、実行前はただの値なので、値の合成などを安心してできる。

### ストリーム

サイズを前提にしないデータ列を副作用なしに変換・合成・遅延評価できる抽象化の仕組み。

- `map`、`filter`、`flatten`などの高階関数で合成可能
- 遅延評価のため、無限列も必要分だけ処理できる
- 使い手は渡されたものから欲しい分だけ取って使う

## 第10章：並行処理

### 共有ミュータブル状態の問題

複数のスレッドからアクセスされるデータは共有ミュータブル状態になる。

### 回避方法

#### 命令型の場合

| 手法 | 説明 |
|------|------|
| **モニターとロック** | リソースには一つのスレッドしかアクセスできないようにする排他ロック |
| **アクターモデル** | オブジェクト間のメッセージ送受信で並行処理を表現。共有メモリを使わず独立して処理 |

#### 関数型の場合

| 手法 | 説明 |
|------|------|
| **アトミック参照** | CAS演算により、ロックフリーでスレッドセーフを実現 |

### スレッドとファイバ

| 種類 | 説明 |
|------|------|
| **スレッド** | メモリ空間を共有するOS管理の実行単位 |
| **ファイバ** | 軽量な仮想スレッド。言語のランタイムが管理し、一つのスレッド上で動く |

goroutineやcoroutineがファイバにあたる。`M:N`モデルでは、複数のスレッドに対して複数のファイバをうまく割り当てて並行処理できる。

## 感想

関数型プログラミングの「なぜそうするのか」が体系的に理解できる良書。特に、純粋関数とイミュータブルな値を使うことで、共有ミュータブル状態という複雑さの根源を根本から排除できるという考え方は説得力があった。「シグネチャに嘘をつかない」という原則を徹底することで、コードの予測可能性と保守性が向上することがよく分かる。
