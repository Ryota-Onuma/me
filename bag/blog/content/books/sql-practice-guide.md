## 読んで得られた学び

本書はSQLの実践的な書き方とパフォーマンスチューニングについて、DBMSの内部動作を踏まえて解説している。特に印象的だったのは、SQLの宣言的な性質を理解し、それを活かしたクエリ設計の重要性。

## DBMSのアーキテクチャ

### 主要コンポーネント

DBMSは以下の主要コンポーネントで構成されている：

- **クエリ評価エンジン**: データアクセスプラン（実行計画）を決定し、最適なアクセスメソッドを選択
- **バッファマネージャ**: メモリ領域の効率的な利用を管理
- **ディスク容量マネージャ**: データの永続化と読み書きを制御
- **トランザクション・ロックマネージャ**: 並行アクセスを安全に管理
- **リカバリマネージャ**: バックアップと復旧を担当

### メモリとストレージの関係

:::important
**バッファキャッシュによる高速化**
アクセス頻度が高いデータをメモリ上のバッファに保持することで、低速なディスクアクセスを最小限に抑える
:::

**バッファの種類**:

1. **データキャッシュ**: ディスク上のデータの一部を保持。ヒット率を高めることが性能向上の鍵
2. **ログバッファ**: 更新処理の情報を一時的に保持。コミット後にまとめてディスクに適用することで、更新処理の非同期化を実現

### コミットの仕組み

:::message
**コミット = ログファイルへの同期書き込み + データキャッシュへの書き込み**
:::

メモリは揮発性のため、コミット時にログファイルへの永続化が成功した時点でコミット完了となる。実際のデータページのディスクへの書き込みは、バックグラウンドで非同期に行われる。

### ワーキングメモリ

`ORDER BY`や`JOIN`などの演算処理で一時的に使用されるメモリ領域。

:::warning
**temp落ちのリスク**
ワーキングメモリが不足すると、ディスクを使用したスワップ（temp落ち）が発生し、パフォーマンスが大幅に低下する
:::

**メモリ割り当ての考え方**:
- 一般的に読み取り処理のほうがデータ量が多いため、`データキャッシュ > ログバッファ`とすることが多い
- ワーキングメモリは複数のSQL実行でシェアされるため、同時実行数を考慮した負荷テストが必要

## クエリ評価エンジンの仕組み

### 主要コンポーネント

1. **パーサー**: クエリの構文解析と変換
2. **オプティマイザ**: 複数の実行計画を生成し、最適なものを選択
3. **カタログマネージャ**: テーブルやインデックスの統計情報を管理
4. **プラン評価**: 選択された実行計画を実行可能なコードに変換

:::important
**統計情報の重要性**
カタログマネージャの統計情報が古いと、オプティマイザが誤った実行計画を作成する可能性がある。統計情報の定期的な更新が必須
:::

### インデックススキャン vs シーケンシャルスキャン

| スキャン方式 | 計算量 | 適している場面 |
|------------|--------|--------------|
| インデックススキャン | O(log N) | データ量が多い場合 |
| シーケンシャルスキャン | O(N) | データ量が少ない場合 |

データ量が少ないうちはシーケンシャルスキャンの方が高速だが、データ量の増加に伴いインデックススキャンが有利になる。

## 条件分岐の実装方法

### UNIONを使った分岐

```sql
SELECT ... WHERE condition1
UNION
SELECT ... WHERE condition2
```

**特徴**:
- 命令的（手続き的）なアプローチ
- 各サブクエリで個別にスキャンが発生するため、パフォーマンス上は推奨されない
- インデックスが極めて効果的に機能する特殊ケースを除き、避けるべき

### CASE式を使った分岐（推奨）

```sql
SELECT 
  CASE 
    WHEN condition1 THEN value1
    WHEN condition2 THEN value2
    ELSE value3
  END AS result
FROM ...
```

**利点**:
- 宣言的なアプローチ
- 一回のスキャンで済むため、パフォーマンスが優れている
- SQLの式指向の性質を活かした書き方

:::tip
**SQLは式が主役**
SQLでは宣言的・式指向の考え方を採用することで、効率的なクエリを書くことができる
:::

## GROUP BYと集約操作

### GROUP BYの役割

`GROUP BY`は「カット（分割）」と「集約」の2つの操作を同時に行う。

**基本構造**:
```sql
SELECT 
  group_key,           -- 集約キー
  COUNT(*),            -- 集約関数
  SUM(column)          -- 集約関数
FROM table
GROUP BY group_key     -- パーティション（部分集合）の作成
HAVING condition       -- 集約後の条件絞り込み
```

:::important
**SELECT句で書けるもの**
GROUP BYを使った場合、SELECT句には以下のみが記述可能：
- 定数
- GROUP BYで指定した集約キー
- 集約関数（COUNT、SUM、AVG、MAX、MINなど）
:::

### GROUP BYの実装アルゴリズム

| アルゴリズム | 特徴 | 適している場面 |
|------------|------|--------------|
| **ハッシュ集約** | メモリ上でハッシュテーブルを使用。ソート不要で高速だが、メモリ不足時はディスクにスピル | キーが少ない場合（低カーディナリティ）<br>メモリに余裕がある場合 |
| **ソート集約** | 先にソートしてから順次集計。メモリ効率は良いがソートコストがかかる | 入力が既にソート済みの場合<br>メモリ制約が厳しい場合 |

:::warning
**ワーキングメモリの確保**
GROUP BYはどちらのアルゴリズムでもワーキングメモリを多く使用する。十分なメモリを確保しないとtemp落ちが発生し、パフォーマンスが大幅に低下する
:::

### GROUP BY vs PARTITION BY

| 機能 | GROUP BY | PARTITION BY (ウィンドウ関数) |
|------|----------|------------------------------|
| **行数の変化** | 減る（集約） | 変わらない |
| **目的** | 集計（要約） | 各行にグループ内の計算結果を付与 |
| **集約** | あり | なし（カットのみ） |
| **使用例** | 部署ごとの合計売上を1行にまとめる | 各社員の行に部署の平均給与を表示 |

### CASE式とGROUP BYの組み合わせ

```sql
SELECT 
  CASE 
    WHEN age < 20 THEN '未成年'
    WHEN age < 65 THEN '成人'
    ELSE '高齢者'
  END AS age_group,
  COUNT(*) AS count
FROM users
GROUP BY 
  CASE 
    WHEN age < 20 THEN '未成年'
    WHEN age < 65 THEN '成人'
    ELSE '高齢者'
  END
```

**実行順序**:
1. 各行に対してCASE式を評価
2. 結果値（'未成年', '成人', '高齢者'）をグループキーとして分類
3. グループごとに集約関数を計算

## SQLのループ処理

:::warning
**細かいSQLのループ実行は避けるべき**
:::

**パフォーマンス低下の理由**:
- SQLのパース処理が繰り返し発生
- コネクション確立とネットワーク転送のオーバーヘッド
- 個々のSQLが小さいため、チューニングの余地が少ない

### 推奨アプローチ

可能な限り、一度のSQLで処理を完結させる。

**ループ回数が決まっている場合**:
- CASE式とウィンドウ関数を使ってハードコーディング

**ループ回数が不定の場合（階層データ）**:
- **隣接リストモデル**: 更新は高速だが検索は遅い（一般的な親子関係の表現）
- **入れ子集合モデル**: 各ノードに左（lft）と右（rgt）の値を割り当て。検索は高速だが更新は遅い

## 結合（JOIN）

### クロス結合（CROSS JOIN）

```sql
SELECT * FROM table1, table2  -- カンマ区切り
SELECT * FROM table1 CROSS JOIN table2  -- 明示的
```

- 2つのテーブルの直積を作成
- パフォーマンスが悪く、実用的なユースケースは稀
- 基本的に使用を避けるべき

### 内部結合（INNER JOIN）

クロス結合の部分集合を取得。相関サブクエリでも同様の結果を得られることがあるが、パフォーマンスはケースバイケース。

### 外部結合（OUTER JOIN）

片方のテーブルにしか存在しない要素をNULLを用いて結果に含める。

:::tip
結合を使った重いSQLは、多くの場合この部分が原因。実行計画の確認と最適化が重要
:::

## サブクエリ

サブクエリは実行中に作成される一時的なテーブルやビューのようなもの。

### パフォーマンス上の問題点

1. **計算コスト**: サブクエリにアクセスするたびに計算が必要
2. **メモリ消費**: ワーキングメモリを使用し、不足時はtemp落ちが発生
3. **最適化の制限**: インデックスなどのメタ情報がないため、オプティマイザの最適化から漏れることがある

### パフォーマンス改善策

**ウィンドウ関数の活用**:
サブクエリの代わりにウィンドウ関数を使うことで、多くの場合パフォーマンスを改善できる。

```sql
-- サブクエリを使った例（非推奨）
SELECT *
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) as rn
  FROM employees
) sub
WHERE rn = 1

-- ウィンドウ関数を直接使った例（推奨）
SELECT *
FROM employees
QUALIFY ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) = 1
```

## SQLチューニングの原則

:::important
**重いSQLへの対処法**
1. まず実行計画を確認する
2. インデックスの有無と使用状況をチェック
3. 統計情報が最新かを確認
4. ワーキングメモリが十分か確認
:::

**基本原則**:
- SQLは宣言的言語であり、処理の詳細はDBMSに任せるが、内部動作の理解はチューニングに不可欠
- 式指向・宣言的な考え方を優先する
- 一度の大きなSQLで処理できるなら、複数の小さなSQLに分けない
- ただし、大きなSQLは実行計画のチューニングが必要になる可能性がある

## まとめ

本書では、SQLの「宣言的」な性質を理解し、それを実践に活かす方法について解説されている。

**主要なポイント**:

1. **式指向の重要性**: UNION（命令的）ではなくCASE式（宣言的）を使うなど、SQLの特性を活かした書き方
2. **内部動作の理解**: バッファ、ワーキングメモリ、実行計画など、DBMSの内部動作を知ることで、なぜそのSQLが遅いのかを論理的に説明できる
3. **ループ vs 集合操作**: アプリケーション側でのループ処理を避け、SQLの集合操作で一度に処理する考え方

SQLを書く際に「どう書くか」だけでなく「なぜそう書くべきか」を理解することで、パフォーマンスを意識したクエリ設計が可能になる。
